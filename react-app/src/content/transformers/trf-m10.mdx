# Module 10: Variants of Transformers — BERT, GPT, and T5

<Bridge>
Modules 1 to 9 built exactly one machine: the original encoder-decoder transformer. In practice almost nobody deploys that whole machine. The field split into three shapes, and the temptation is to memorise them as three separate architectures. They are not. They are three settings of the same two dials — and once you can see the dials, the rest follows.
</Bridge>

## Two dials, three architectures

Every attention layer in this track has done the same thing: compute queries, keys, and values from some set of vectors, then let each position pull information from whichever positions matter to it. Everything that separates BERT from GPT from T5 is a choice about two questions:

1. **Where do Q, K, and V come from?** Same sequence (self-attention) or two different sequences (cross-attention)?
2. **Which positions are allowed to see which?** Everything (bidirectional) or only what came before (causal)?

That is the whole design space. The three famous families are just the three combinations anyone found useful.

Every architectural family is a setting of those two dials." },
]} />

## Encoder-decoder: the complete machine

<PredictReveal
  prompt="In the decoder's cross-attention layer, the queries come from one stack and the keys and values from the other. Which way round is it, and why?"
  options={["Q from the encoder — the source text asks what to produce", "Q from the decoder — the thing being written asks what is relevant in the input"]}
  correct={1}
>

<VariantsWidget />

The input is encoded once, in full, before generation starts. The decoder then generates one token at a time, reaching back into that encoding through cross-attention whenever it needs to.

The direction matters. Queries come from the **decoder** — the thing currently being generated, which is the thing asking a question. Keys and values come from the **encoder output** — the material being searched. Reverse it and the model would be using the untranslated source words as the question rather than as the answer, which is backwards from how information actually needs to flow.

  { t: 'Encoder', d: 'Bidirectional self-attention + feed-forward, ×N. Every input token sees every other input token, both directions, before generation starts.' },

  { t: 'Decoder self-attn', d: 'Masked (causal): each output position sees only itself and earlier output positions.' },
  { t: 'Cross-attention', d: 'Q from the decoder, K and V from the encoder output. The only place the two stacks meet.' },
  { t: 'Models', d: 'T5, BART, MarianMT, and the original 2017 Transformer.' },
  { t: 'Use when', d: 'Input and output are genuinely different sequences — translation, summarisation, speech-to-text.' },
]} />

</PredictReveal>

## Decoder-only: delete the encoder

<PredictReveal
  prompt="A decoder-only model has no encoder and no cross-attention at all. So how does it read the prompt?"
  options={["A separate first pass over the prompt before generation begins", "The prompt is simply the earliest positions of the same sequence it is writing"]}
  correct={1}
>

Drop the encoder and cross-attention entirely. Put the prompt and the generated tokens in **one sequence**, and causal masking already does the encoder's job — any later token can attend back to every earlier token, which includes the entire prompt. There is nothing left for a separate encoder to contribute.

This is why the family that looks like it removed the most capability ended up dominating: concatenation plus causal masking absorbs the encoder, and what remains is simpler, trains on any raw text, and does one thing at inference that it also did at training.

  { t: 'Models', d: 'GPT, LLaMA, Claude, Falcon.' },
  { t: 'Use when', d: 'The output continues or extends the input open-endedly — chat, completion, code, most current LLM use.' },
]} />

</PredictReveal>

## What decoder-only gives up

<PredictReveal
  prompt="Decoder-only models dominate today. Does that mean the design has no cost compared with encoder-decoder?"
  options={["Correct — it is strictly better, which is why it won", "There is a real cost: prompt tokens never get a bidirectional pass over each other"]}
  correct={1}
>

There is a genuine trade-off, and it is worth being precise about it. In an encoder-decoder, the prompt gets a dedicated bidirectional pass: every prompt token is refined against every other prompt token, in both directions, before a single output token is committed to. In a decoder-only model that never happens — a prompt token can only ever see prompt tokens to its left.

So disambiguation that an encoder would have resolved upfront has to happen **downstream**, through more attention hops in later layers. The information is still reachable, because generation always happens after the full prompt has been read; it just costs depth rather than being handled in one dedicated pass.

That is the trade the field made: give up the bidirectional prompt pass, get a simpler model that trains on undifferentiated text at enormous scale. At sufficient scale, depth turned out to buy back what the encoder was doing.

</PredictReveal>

<Recall items={[
  { q: "What is the practical cost of decoder-only compared with encoder-decoder?", a: "Prompt tokens never get a bidirectional pass over each other — each one sees only prompt tokens to its left. Disambiguation an encoder would have resolved upfront must instead happen downstream through more attention hops in later layers. The information stays reachable, since generation happens after the whole prompt is read, but it costs depth rather than one dedicated pass." },
]} />

## Encoder-only: delete the decoder

<PredictReveal
  prompt="An encoder-only model produces one contextual vector per input token. For a whole-sentence judgment like spam or not-spam, which vector does the classifier read?"
  options={["The average of every token vector", "The final vector of a [CLS] token prepended to the input"]}
  correct={1}
>

The same encoder block, standalone. Nothing gets generated — the output is a judgment about the text, read off its final vectors.

A **[CLS]** token is prepended to the input. It starts with no meaning of its own, which is exactly the point: bidirectional attention across N layers lets it accumulate information from every other token without carrying any lexical baggage of its own. Its final vector ends up functioning as a learned summary of the whole sequence, which a small classifier head can read.

Not every task needs that summary. Per-token tasks like named entity recognition skip pooling entirely and classify each token's own final vector directly.

## The mask decides the training objective

Because the mask determines what a model can see, it also determines what you are able to *train* it on.

<PredictReveal
  prompt="An encoder-only model sees the entire sentence at once, in both directions. Why can it not be trained on the same next-token prediction objective GPT uses?"
  options={["Next-token prediction would work, it is just slower in an encoder", "With no causal mask the answer is already visible — predicting the next token would be copying a token the model can see"]}
  correct={1}
>

Bidirectional attention makes next-token prediction useless: position 5 can attend directly to position 6, so predicting position 6 teaches nothing. Encoder-only models are instead trained with **Masked Language Modelling (MLM)** — a fraction of input tokens are hidden and the model predicts each from the tokens on both sides. Nothing leaks, because the target genuinely is not in the input.

Decoder-only models have the opposite situation. The causal mask already hides the future, so **Causal Language Modelling (CLM)** is legitimate at every position simultaneously — exactly the parallel cross-entropy loss from Module 9.

Encoder-decoder models are trained on **text-to-text** pairs: unmasked encoder, causal decoder, next-token loss over the target.

</PredictReveal>

<Recall items={[
  { q: "Why is Masked Language Modelling used for encoder-only models rather than next-token prediction?", a: "An encoder has no causal mask, so every token can already see every other token. Predicting the next token would just be copying something visible. Masking tokens out of the input creates a genuine prediction problem that requires combining context from both directions." },
]} />

## At a glance

| Architecture | Attention used | Cannot do | Typical task | Example model |
|---|---|---|---|---|
| **Encoder-decoder** | Bidirectional (encoder) + causal (decoder) + cross-attention | — | Translation, summarisation | T5, BART |
| **Decoder-only** | Causal self-attention only | True bidirectional context in one pass | Chat, open-ended generation | GPT, LLaMA |
| **Encoder-only** | Bidirectional self-attention only | Generate new text | Classification, embeddings, NER | BERT |

The **Cannot do** column is the one worth memorising. Each family is defined as much by the capability it gave up as by the one it kept.

<ConceptBox title="TL;DR">
- Every variant is a choice on two dials: where Q, K and V come from, and which positions may attend to which.
- **Encoder-decoder** is the complete machine — bidirectional encoder, causal decoder, joined by cross-attention with Q from the decoder and K/V from the encoder output.
- **Decoder-only** deletes the encoder because concatenation plus causal masking already does its job. The cost is that prompt tokens never get a bidirectional pass, so disambiguation moves downstream into extra depth.
- **Encoder-only** deletes the decoder and reads a judgment off the final vectors — the `[CLS]` vector as a learned whole-sequence summary, or each token's own vector for per-token tasks.
</ConceptBox>
