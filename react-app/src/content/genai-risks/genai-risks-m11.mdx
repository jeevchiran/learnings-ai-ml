## Attack the capability factor, not just the text

<PredictReveal
  prompt="A team is deciding where to invest defensive effort: better detection of hostile text entering the model, or tighter limits on what the model is allowed to do with tools. Which yields the more durable guarantee?"
  options={["Detection — stopping the attack at the input is always preferable to containing it later", "Capability limits — they hold regardless of whether any given payload was detected, whereas detection fails open on the first phrasing nobody anticipated"]}
  correct={1}
>

Both matter, but only one degrades gracefully. Text detection (Module 9) is probabilistic against an unbounded input space, and when it misses, nothing else stops the action. Capability constraints are deterministic and enforced outside the model, so they hold even against a payload nobody has seen. This is the same reasoning that puts a database permission model underneath application input validation rather than relying on validation alone.

<FactList accent="#b91c1c" items={[
  { t: 'Least privilege for tools', d: 'Grant the narrowest scope that supports the task — read-only where reads suffice, one mailbox rather than the mail account, a scoped API token rather than an admin one. Caps the blast radius of any successful injection.' },
  { t: 'Privilege separation', d: 'Do not let one context hold both untrusted content and high-privilege capability. Summarising a hostile document is safe if the summarising context has no tools; the planning context that does have tools should not ingest raw external text.' },

  { t: 'Provenance tracking', d: 'Tag content by trust level as it enters the system, and let downstream policy depend on those tags — the enforced boundary the model itself does not have.' },

## The text-layer defences still earn their place

<PredictReveal
  prompt="Given that no prompt-level defence is categorical, is there still value in spotlighting — clearly marking where untrusted content begins and ends and instructing the model to treat it as data?"
  options={["No — since it is not a guarantee, it provides no meaningful protection", "Yes — it measurably shifts the statistical competition from Module 7, and layers that reduce probability are worth having even when they cannot eliminate it"]}
  correct={1}
>

The Module 7 conclusion is that wording cannot be *categorical*, not that it is useless. Spotlighting — delimiting untrusted spans, marking them explicitly as data, and instructing the model to treat any instructions inside them as content to report rather than commands to follow — meaningfully raises the bar, and combines with everything else.

The text-layer stack worth having: spotlight and delimit untrusted content; strip or neutralise invisible text, comments, and metadata before ingestion, so hidden payloads lose their asymmetry; filter output for exfiltration patterns before rendering; and constrain output format where possible, since a response required to be structured JSON has less room to carry an attacker's free text.

None of these is a boundary. All of them lower probability, and they sit on top of controls that hold when they fail.

</PredictReveal>

## Operating it, not just building it

<PredictReveal
  prompt="A system passes an injection red-team exercise before launch. How long does that result remain valid?"
  options={["Indefinitely for that architecture, as long as the code does not change", "Only until the inputs, tools, model version, or attack techniques change — which is continuously"]}
  correct={1}
>

Injection resistance is not a property that can be established once. The corpus gains documents, a tool gains a new scope, the model is upgraded and its instruction-following tendencies shift slightly, and public technique catalogues advance. The operational layer is therefore part of the design: automated injection test suites in CI, red-teaming that includes indirect vectors rather than only typed prompts, logging of every tool call with its triggering context so an incident can be reconstructed, and monitoring for the shapes that indicate exfiltration attempts.

Closing the loop with the first half of this track: both hallucination and injection resist elimination and both are managed by stacking imperfect layers around a model whose behaviour is probabilistic. The difference is the threat model — accidental failure versus an adversary who adapts to your defences — which is exactly why the injection stack leans on deterministic controls outside the model rather than on the model behaving well.

</PredictReveal>

<ConceptBox title="TL;DR">
- Risk is **untrusted input × unsupervised capability**, and the capability factor is where durable guarantees live — least privilege, privilege separation, human confirmation for consequential actions, egress allowlists, provenance tagging.
- Capability controls **degrade gracefully**; text detection **fails open**, because natural language offers an unbounded space of phrasings.
- Text-layer defences — spotlighting, stripping hidden text and metadata, output filtering, constrained formats — are still worth stacking: they lower probability even though they cannot create a boundary.
- Injection resistance is **operational, not one-time**: CI injection tests, red-teaming that covers indirect vectors, tool-call logging, and exfiltration monitoring.
- Both halves of this track end the same way — imperfect layers around a probabilistic model — but injection adds an **adversary who adapts**, which is why its controls sit outside the model.
</ConceptBox>
