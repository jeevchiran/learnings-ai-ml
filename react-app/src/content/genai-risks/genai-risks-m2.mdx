# Module 2: Classifying Hallucinations

<Bridge>
Module 1 gave one word for the whole phenomenon. That word covers failures with different causes, different detection methods, and different fixes — so before diagnosing anything, it needs to be split along the dimensions that actually change what you do about it.
</Bridge>

## Three independent dimensions

<PredictReveal
  prompt="A model summarising a document invents a statistic that happens, by coincidence, to be true about the world. Is that a hallucination?"
  options={["No — the claim is true, so nothing was hallucinated", "Yes — it is unsupported by the source it was asked to summarise, which is the standard the task is judged against"]}
  correct={1}
>

<HallucinationTaxonomyWidget />

That case is the clearest argument for splitting the term. It is a **faithfulness** failure (unsupported by the given source) without being a **factuality** failure (false about the world). A summarisation system that fabricates true-but-unsourced claims is still broken — users of a summariser are relying on it to represent the document, not to add outside knowledge.

## Severity is a separate axis again

<PredictReveal
  prompt="Two hallucinations in the same system: one misstates a historical date in a trivia answer, the other invents a drug interaction in a medical summary. Should a production system treat these as the same class of failure?"
  options={["Yes — both are unsupported claims, so both count identically when measuring the hallucination rate", "No — consequence is an independent axis, and a single aggregate rate hides the failures that actually matter"]}
  correct={1}
>

A single "hallucination rate" treats a wrong date and an invented drug interaction as one unit each. That aggregate is close to useless for deciding whether a system is safe to deploy, because the distribution of *consequence* matters far more than the count. Production evaluation therefore stratifies: rate per claim type, per domain, and per severity tier, with a much lower tolerance for claims that touch safety, legal, or financial decisions.

This is also why detection strategy follows classification. Intrinsic failures can be caught by checking the output against the context programmatically. Extrinsic failures need an external knowledge source or a retrieval step. High-severity claims in either category are where human review gets spent — Module 6 returns to this.

</PredictReveal>

---

<ConceptBox title="TL;DR">
- **Intrinsic vs. extrinsic**: does the output contradict the supplied context, or add content the context is silent on? This determines whether automated detection is even possible from the prompt alone.
- **Faithfulness vs. factuality**: unsupported by the given source, versus false about the world. A true-but-unsourced claim in a summary is a real failure — the dimensions are independent.
- **Closed vs. open domain**: whether a source was provided sets which of those two standards applies.
- **Severity** is a fourth, independent axis. A single aggregate rate hides the consequence distribution that actually decides deployability.
</ConceptBox>
