# Module 4: Image Embeddings and Vector Representations

<ConceptBox title="TL;DR">
- An **embedding** is the vector a network produces just before its classifier — 512 numbers for ResNet-18, 2048 for ResNet-50.
- It is a **learned coordinate system** in which semantically similar images are close. Raw pixels are not: two photos of the same cat can be further apart in pixel space than a cat and a car.
- **L2-normalise, then use cosine.** After normalisation cosine and Euclidean rank identically, because $\|a-b\|^2 = 2 - 2\cos(a,b)$.
- Embeddings decouple representation from task: **add a new class without retraining anything** by adding vectors to an index.
- The classifier is a thin layer on top. Removing it does not remove the intelligence — it removes the opinion.
</ConceptBox>

## Pixels are a terrible coordinate system

Two 224×224 RGB images live in $\mathbb{R}^{150528}$. In that space, distance measures *pixel-wise agreement*, which has almost nothing to do with content:

- Shift an image one pixel right → every coordinate changes → enormous distance, identical content.
- Brighten it by 10% → large distance, identical content.
- A dark cat and a dark car → small distance, unrelated content.

A trained network's penultimate layer is a space where those pathologies are largely gone, because the training objective *forced* it: to separate 1,000 classes linearly at the last layer, everything before it must arrange images so that classes are linearly separable — which means semantically alike images end up near each other.

## Getting an embedding

```python
import torch, torch.nn as nn, torchvision
import torch.nn.functional as F

backbone = torchvision.models.resnet18(weights='DEFAULT')
backbone.fc = nn.Identity()          # 512-d output instead of 1000 logits
backbone.eval()

@torch.no_grad()
def embed(batch):                    # batch: (B, 3, 224, 224), ImageNet-normalised
    v = backbone(batch)              # (B, 512)
    return F.normalize(v, dim=1)     # L2-normalise → every vector on the unit sphere

e = embed(images)
sim = e @ e.T                        # (B, B) cosine similarity, one matmul
```

That `e @ e.T` is the whole of similarity search at small scale: after normalisation, **cosine similarity is just a dot product**.

<ConceptBox title="Why L2-normalise">
Raw feature vectors have magnitudes that vary with image contrast, texture density and how confidently the network fires. That magnitude is mostly nuisance, and it dominates Euclidean distance.

Normalising puts every vector on the unit sphere so only *direction* — the pattern of which features fired, not how hard — carries information. After that:

$$\|a - b\|^2 = \|a\|^2 + \|b\|^2 - 2a\cdot b = 2 - 2\cos(a, b)$$

so Euclidean distance is a monotone function of cosine similarity, and the two produce **identical rankings**. Pick whichever your index supports; do not agonise over it.
</ConceptBox>

## Which layer, and why not the logits

| Layer | Dim | Character |
|---|---|---|
| conv features (before pooling) | 7×7×512 | spatial, huge, good for segmentation — this becomes U-Net's skip |
| **after global average pool** | 512 | the standard embedding — position discarded, semantics kept |
| logits | 1000 | ImageNet's *opinion*, not a general representation |
| softmax probabilities | 1000 | worse still — squashed, and mostly zeros |

Use the pooled features. The logits are a projection onto 1,000 specific classes; two images of an object ImageNet has never seen may get nearly identical (uninformative) logits while their pooled features are clearly distinct.

## What embeddings buy you

**Zero-shot extension.** Add a new product to a catalogue by embedding one photo and inserting it into the index. A classifier would need retraining and a new output unit.

**Retrieval and dedup.** "Find visually similar items", reverse image search, near-duplicate detection — all nearest-neighbour queries.

**Clustering unlabelled data.** Run k-means on embeddings to discover structure before you have labels.

**Cheap downstream models.** Embed once, then train a logistic regression in seconds — the linear probe from Module 3.

## Worked example — the index, and when brute force stops working

$N$ images, $d$-dimensional embeddings, one query:

$$\text{brute force} = O(Nd) \text{ multiply-adds}$$

For $N = 10^6$, $d = 512$: $5.12 \times 10^8$ operations per query — a few hundred milliseconds on a CPU, and it scales linearly. At $10^8$ images it is hopeless.

Approximate nearest neighbour (FAISS, HNSW, ScaNN) trades a little recall for sub-linear search:

| Index | Build | Query | Recall@10 |
|---|---|---|---|
| Flat (brute force) | none | $O(Nd)$ | 1.00 |
| IVF (inverted file) | k-means over the space | $O(\tfrac{N}{k}d)$ | ~0.95 |
| HNSW (graph) | greedy graph | $O(d\log N)$ | ~0.98 |
| + PQ (product quantisation) | codebooks | as above, 8–32× less memory | ~0.90 |

Memory matters as much as speed: $10^6 \times 512 \times 4$ bytes $= \mathbf{2.05\ \text{GB}}$ in float32. Product quantisation compresses that to tens of megabytes, which is the difference between fitting in RAM and not.
