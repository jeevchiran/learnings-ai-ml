## The architecture

<UNetWidget />

**Contracting path** (4 levels, repeated):
1. 3×3 conv → ReLU
2. 3×3 conv → ReLU
3. 2×2 max-pool, stride 2 — halves size, and channels double at the next level

**Bottleneck**: two 3×3 convs at 1024 channels.

**Expanding path** (4 levels, repeated):
1. 2×2 up-conv — doubles size, halves channels
2. **concatenate** the cropped encoder map from the same level
3. 3×3 conv → ReLU
4. 3×3 conv → ReLU

**Head**: 1×1 conv mapping 64 channels to the number of classes.

</PredictReveal>

They hand the decoder full-resolution feature maps that never passed through the bottleneck, so boundary information destroyed by pooling is available again when the output is produced. Everything else is a standard encoder-decoder." },
]} />

## Why the output is smaller than the input

<PredictReveal
  prompt="The original U-Net takes a 572x572 input through unpadded 3x3 convolutions all the way down and back up. What size is the final output?"
  options={["572x572 — padding is implicit", "570x570 — just a few pixels lost", "388x388 — the shrinkage compounds through the depth"]}
  correct={2}
>

Every unpadded 3×3 conv removes a one-pixel border, so each level loses 4 pixels (two convs, two pixels each side). Compounded through the depth:

$$572 \xrightarrow{\text{2 convs}} 568 \xrightarrow{\text{pool}} 284 \xrightarrow{\text{2 convs}} 280 \xrightarrow{\text{pool}} 140 \to 136 \to 68 \to 64 \to 32 \to 28$$

then back up, ending at **388**. The widget shows every one of these numbers.

<ConceptBox title="Overlap-tile: what the shrinkage is actually for">
It looks like a defect. It was a deliberate choice for large microscopy images that do not fit in memory.

To segment a big image you feed **overlapping 572² tiles** and keep only the valid 388² centre of each output. Every predicted pixel therefore had its full receptive field available inside the tile — no tile ever has to guess at its own border. Padding, by contrast, fabricates context at every tile edge, and those fabrications show up as seams.

The cost is that the border region must come from *somewhere*: the paper mirrors the image at the true boundary. Modern implementations mostly pad and accept slightly worse edges, because whole images now fit in memory.
</ConceptBox>

</PredictReveal>

## The two variants you will actually meet

**Padded U-Net.** Set `padding=1` on every 3×3 conv. Output size equals input size, skips need no cropping, and the code is far simpler. This is what almost every library ships.

**Pretrained-encoder U-Net.** Replace the contracting path with a ResNet/EfficientNet backbone and take skips from its intermediate stages. This is the single highest-value change for small datasets — it is Module 2's argument applied to segmentation:

```python
# segmentation_models_pytorch makes this a one-liner
import segmentation_models_pytorch as smp

model = smp.Unet(
    encoder_name='resnet34',        # contracting path = pretrained ResNet-34
    encoder_weights='imagenet',     # ← the transfer learning from Modules 1-3
    in_channels=3,
    classes=1,                      # binary segmentation
)
```

## Data efficiency, and the augmentation that mattered

<PredictReveal
  prompt="U-Net won the 2015 ISBI cell-tracking challenge. Roughly how many training images did it use?"
  options={["30", "300", "3,000"]}
  correct={0}
>

U-Net won the 2015 ISBI cell-tracking challenge trained on **30 images**. The architecture is only half of that story; the other half is **elastic deformation** — randomly warping the image with a smooth displacement field.

That choice is domain reasoning, not a generic trick: cells and tissue genuinely deform, so a warped training image is still a *realistic* image, and the network learns invariance to exactly the variation the domain contains. The general lesson is that the best augmentation encodes a true symmetry of your data — which is also why rotation is right for microscopy and wrong for street scenes.

</PredictReveal>

The same reasoning explains why rotation suits microscopy and not street scenes, where up is a real and stable cue." },

## Worked example — where the parameters are

<PredictReveal
  prompt="Base 64, depth 4, 2 classes. Which part of the network holds the most parameters?"
  options={["The contracting (encoder) path", "The bottleneck", "The expanding (decoder) path"]}
  correct={1}
>

Base 64, depth 4, 2 classes:

| Part | Params |
|---|---|
| Contracting path | ~4.7M |
| Bottleneck (512→1024→1024) | ~14.2M |
| Expanding path | ~12.1M |
| 1×1 head (64→2) | 130 |
| **Total** | **31,030,658** |

Nearly half sits in the bottleneck, because parameters scale with $C_{in} \times C_{out}$ and that is where both are largest. Halving `base` to 32 divides the total by roughly **4** — the first knob to reach for when a U-Net overfits, and usually more effective than adding dropout.

<ConceptBox title="TL;DR">
- U-Net is an encoder-decoder with **long concatenative skips at every level**. That is the entire innovation, and it is why boundaries stay sharp.
- The original (Ronneberger et al., 2015) uses **unpadded** 3×3 convs, so 572² in becomes **388² out**, and each skip must be **centre-cropped** before concatenation.
- Channels double on the way down (64→1024) and halve on the way up. **31,030,658 parameters** at base 64.
- It was designed for **biomedical images with very few labels**, and the augmentation strategy (elastic deformation) was as important as the architecture.
- Modern variants: pad the convs (no cropping), swap the encoder for a pretrained backbone, add BatchNorm. The U stays.
</ConceptBox>
