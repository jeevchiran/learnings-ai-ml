# Build — Feature Generation

## The shape of a training row

```python
labels = pd.DataFrame({
    "user_id": ["U2"],
    "item_id": ["P4"],
    "as_of":   [pd.Timestamp("2026-03-08")],   # when the decision was made
    "label":   [1],
})
```

`as_of` is the timestamp of the impression or decision being modelled — not "now", not the end of the training window. Every feature attached to this row must be computable from events strictly before it.

```python
def as_of_user_features(labels, events, windows=(1, 7, 30)):
    out = labels.copy()
    for w in windows:
        counts = []
        for r in labels.itertuples():
            lo = r.as_of - pd.Timedelta(days=w)
            mask = ((events.user_id == r.user_id)
                    & (events.event_ts <  r.as_of)      # STRICT — not <=
                    & (events.event_ts >= lo))          # bounded window
            counts.append(int(mask.sum()))
        out[f"u_events_{w}d"] = counts
    out["u_burst"] = out["u_events_1d"] / (out["u_events_7d"] / 7 + 1)
    return out
```

The loop makes the exact time window easy to inspect. At scale, optimize it while checking against this reference. A backward `merge_asof` is useful for looking up historical snapshots. For example, the following computes a **cumulative count before each decision**, not a 30-day count:

```python
# Count all events up to each recorded timestamp, including timestamp ties.
history = (events.groupby(["user_id", "event_ts"])
                 .size().rename("events_at_time").reset_index()
                 .sort_values("event_ts"))
history["u_events_before_as_of"] = history.groupby("user_id")["events_at_time"].cumsum()

feats = pd.merge_asof(
    labels.sort_values("as_of"),
    history,
    left_on="as_of", right_on="event_ts", by="user_id",
    direction="backward", allow_exact_matches=False,   # ← this flag IS the strict <
)
feats["u_events_before_as_of"] = feats["u_events_before_as_of"].fillna(0).astype(int)
```

`allow_exact_matches=False` excludes events at the decision timestamp. A rolling count looked up at the most recent event is **not** an exact 30-day count at the decision time: events may have expired since that last event. Use the reference loop above, or subtract cumulative counts at both window boundaries. Test boundary timestamps and users with no history.

## User × item features — the ranker's edge

```python
def as_of_pair_features(labels, events):
    out = labels.copy()
    views, carts, days_since = [], [], []
    for r in labels.itertuples():
        h = events[(events.user_id == r.user_id)
                   & (events.item_id == r.item_id)
                   & (events.event_ts < r.as_of)]
        views.append(int((h.event_type == "view").sum()))
        carts.append(int((h.event_type == "cart").sum()))
        days_since.append((r.as_of - h.event_ts.max()).days if len(h) else 999)
    out["ui_views"], out["ui_carts"], out["ui_days_since"] = views, carts, days_since
    return out
```

`999` as the "never interacted" sentinel works for tree models, which will split on it. It would be poison for a linear model or a neural net, where it distorts every scale — use a separate `ui_never_seen` boolean there instead.

## Item features need a historical snapshot

```python
# WRONG — today's catalog values pasted onto year-old rows
feats = labels.merge(catalog[["item_id", "price", "return_rate"]], on="item_id")

# RIGHT — as-of join against a versioned snapshot table
feats = pd.merge_asof(
    labels.sort_values("as_of"),
    catalog_history.sort_values("valid_from"),      # item_id, price, return_rate, valid_from
    left_on="as_of", right_on="valid_from", by="item_id",
    direction="backward",
)
```

The catalog table has no history unless you built it one. `price` today is not the price at the moment of a decision six months ago, and `return_rate` today includes returns that had not happened yet. Keeping a slowly-changing-dimension table is unglamorous infrastructure that decides whether your item features are usable at all.

<ConceptBox title="Training/serving skew — the same value, twice">
Every offline feature needs an online counterpart producing **the identical value**. Two implementations of `u_events_30d` — one Spark, one Redis — will disagree, and the model was trained on only one of them.

The three real defences, in ascending cost and effectiveness:

1. **One definition, two runtimes.** Write the feature once in a shared library; the batch job and the serving path both call it.
2. **Log the features you served.** Then train on *those* rows next time. The distributions match by construction because they are the same rows.
3. **A feature store.** Feast, Tecton and friends exist for exactly this: one definition, offline point-in-time joins and online lookups from the same registry.

Option 2 is underrated. It costs a logging change, needs no new infrastructure, and eliminates the skew entirely for everything after the first model.
</ConceptBox>

---

<ConceptBox title="TL;DR">
- Every feature is an **as-of join**: aggregate events with `event_ts < row.as_of`, bounded below by a window.
- The label row carries an `as_of` timestamp. Everything is computed relative to it. No exceptions.
- Check that every contributing event precedes the row's `as_of` timestamp. A historical count cannot exceed the whole-log count, but equality can be valid when there are no later events. A smaller count alone does not prove that the right events were used.
- Build user, item and **user×item** features. The last family is the ranker's only real advantage over retrieval.
</ConceptBox>
