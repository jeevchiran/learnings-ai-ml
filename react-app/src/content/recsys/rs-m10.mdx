<ConceptBox title="TL;DR">
- Features come in four families: **user**, **item**, **user×item cross**, and **context**. The cross features are where the ranker earns its keep — retrieval structurally cannot use them.
- Every aggregate must be **point-in-time correct**: computed only from events strictly *before* the row's timestamp. This is the single most common production recsys bug.
- **Time decay** replaces a count with $\sum w \cdot 2^{-\Delta t / t_{1/2}}$, so *when* stops being thrown away. Half-life is the knob.
- **Popularity** is a family, not one number: global, windowed, category-relative, trend ratio, rank percentile.
- **Session features** are the shortest-lived and highest-signal of all — last item, last N, dwell time, category share. Dwell is what separates real interest from a bounce.
- **MF scores are features.** Feeding the ALS score into the ranker is how retrieval and ranking actually compose: it supplies collaborative structure the ranker cannot learn from few labels.
</ConceptBox>

## The four families

| Family | Examples | Changes |
|---|---|---|
| **User** | 30d purchase count, average order value, category affinity vector, days since first order | Daily |
| **Item** | 7d sales rank, price, discount %, return rate, days since listing, stock level | Hourly |
| **User × item** | Times this shopper viewed *this* item, did they cart it, affinity between their category vector and this item's category | Per request |
| **Context** | Hour of day, device, referrer, current session length, item currently being viewed | Per request |

The cross family matters most and is most often skipped. Retrieval **cannot** use it: two-tower and MF architectures compute user and item vectors independently so the item index can be precomputed. Only after retrieval, with a few hundred candidates in hand, can you afford to compute something that depends on both sides. **A ranker without cross features is a re-implementation of retrieval.**

## Point-in-time correctness

<FeatureWindowWidget />

The rule is one character wide:

```sql
-- WRONG: reads the whole log, including the future
SELECT user_id, COUNT(*) AS views_30d
FROM events GROUP BY user_id

-- RIGHT: strictly before this row's timestamp, bounded window
SELECT l.user_id, l.event_ts,
       COUNT(e.event_id) AS views_30d
FROM labels l
LEFT JOIN events e
  ON  e.user_id = l.user_id
  AND e.event_ts <  l.event_ts                        -- strict: no ties
  AND e.event_ts >= l.event_ts - INTERVAL '30' DAY
GROUP BY l.user_id, l.event_ts
```

Two details that look pedantic and are not:

- **`<` not `<=`.** With second-granularity timestamps, the click you are predicting can share a timestamp with the label. `<=` puts the answer in the feature.
- **Bounded below.** Without the lower bound the "window" is all history, which makes the feature drift as the dataset ages and makes it non-reproducible.

<ConceptBox title="Common confusion — 'my split is temporal, so my features are safe'">
No. They are independent bugs.

A clean temporal split guarantees no **event** from the test period appears in training. It says nothing about the **features** attached to training rows. If `user_30d_purchases` was computed with one `GROUP BY` over the full table, every training row carries a value that already knows about the test period.

The symptom is distinctive: offline AUC is excellent, feature importance is dominated by one aggregate, and the online lift is zero. The bug is not in the model code at all — it is in the SQL, which is why it survives code review.
</ConceptBox>

## Multi-window aggregates

One window is a level. Two windows are a **trend**, and trend is usually the stronger signal:

```python
feats["views_1d"]     = window(events, days=1)
feats["views_7d"]     = window(events, days=7)
feats["views_30d"]    = window(events, days=30)
feats["burst_ratio"]  = feats["views_1d"] / (feats["views_7d"] / 7 + 1)   # +1 guards /0
```

`burst_ratio` fires when an item is trending *right now* relative to its own baseline — which is exactly what a "trending" row needs and what a raw 30d count can never express. The same trick on the user side separates "browsing hard today" from "steady long-term customer".

But windows are still a blunt instrument: inside a 30-day window, an event from yesterday and one from four weeks ago count the same, and one day later the old event drops off a cliff. Decay fixes both.

## Recency with time decay

A count throws away *when*. Decay keeps it:

$$a_{ui}(t) = \sum_{e \,\in\, \text{events}(u,i),\; t_e < t} w_{\text{type}(e)} \cdot 2^{-(t - t_e)/t_{1/2}}$$

Plain English: add up the event weights, but shrink each one by half for every half-life that has passed since it happened.

<DerivationSteps>
<DerivationStep number={1} title="Why base 2 and a half-life">
$2^{-\Delta t / t_{1/2}}$ and $e^{-\lambda \Delta t}$ are the same curve — $\lambda = \ln 2 / t_{1/2}$. Use the half-life form because the parameter is directly interpretable: "$t_{1/2} = 7$" means *an event one week old counts half as much*. Nobody can reason about $\lambda = 0.099$.
</DerivationStep>

<DerivationStep number={2} title="It degenerates to the things you already know">
As $t_{1/2} \to \infty$ the weights all approach 1 and you are back to a raw lifetime count. As $t_{1/2} \to 0$ only today survives. **Windowed counts are the crude special case**: a hard 0/1 weight with the cliff at the window edge. Decay is a smooth window with no cliff.
</DerivationStep>

<DerivationStep number={3} title="It is incrementally updatable">
$$a(t_2) = a(t_1) \cdot 2^{-(t_2-t_1)/t_{1/2}} + \text{(new events)}$$
Decay past state, add what arrived. You never re-scan history, so this is cheap in a streaming feature store — unlike a sliding window, which must remember every event in order to expire it.
</DerivationStep>
</DerivationSteps>

<TimeDecayWidget />

**Worked example.** Bhavna's raw affinities as of day 24: Keyboard = 4, Steel Bottle = 4. A dead tie, and the count cannot break it. Her Keyboard cart was day 8; her Bottle cart was day 14. With $t_{1/2}=7$:

$$a_{\text{Bottle}} = 1 \cdot 2^{-23/7} + 3 \cdot 2^{-10/7} = 1.22, \qquad a_{\text{Keyboard}} = 1 \cdot 2^{-17/7} + 3 \cdot 2^{-16/7} = 0.80$$

The tie breaks toward the Bottle, on recency alone. Whether that is *right* is an empirical question — Bhavna in fact buys the Keyboard on day 27 — and that is the honest lesson: **decay is a hypothesis about how fast interest fades, and the half-life is what you tune.** Groceries and laptops are not the same problem, and the same store often needs different half-lives per category.

```python
def decayed_affinity(events, user, as_of, half_life=7.0):
    h = events[(events.user_id == user) & (events.event_ts < as_of)]   # strict <
    age = (as_of - h.event_ts).dt.total_seconds() / 86400
    return (h.weight * np.power(2.0, -age / half_life)).groupby(h.item_id).sum()
```

Ship two or three half-lives (say 1d, 7d, 30d) as separate features rather than agonising over one. The model will learn which timescale matters, and their ratios encode trend for free.

## Popularity features

"Popularity" is not one number. Each variant answers a different question, and shipping only the first is the common mistake:

| Feature | Question | Failure it avoids |
|---|---|---|
| `pop_all` | Total distinct users, all time | — (the naive one) |
| `pop_short` / `pop_long` | Distinct users in 3d / 14d | All-time counts never forget a dead hit |
| `pop_trend` | short rate ÷ long rate | Distinguishes *rising* from *big* |
| `pop_cat_share` | Share of its own category | Lets a niche item be a big fish in a small pond |
| `pop_rank_pct` | Rank percentile in [0,1] | Scale-free; survives catalog growth and seasonality |

```python
def popularity_features(events, as_of, short=3, long=14):
    before = events[events.event_ts < as_of]                       # point-in-time
    win = lambda d: (before[before.event_ts >= as_of - pd.Timedelta(days=d)]
                       .groupby("item_id")["user_id"].nunique())
    s, l = win(short), win(long)
    out = pd.DataFrame({"pop_all": before.groupby("item_id")["user_id"].nunique(),
                        "pop_short": s, "pop_long": l}).reindex(ITEMS).fillna(0)
    out["pop_trend"]     = (out.pop_short / short) / (out.pop_long / long + 0.01)
    out["pop_rank_pct"]  = out.pop_long.rank(pct=True)
    out["pop_cat_share"] = out.pop_long / out.join(catalog.cat).groupby("cat").pop_long.transform("sum")
    return out
```

<ConceptBox title="Three traps in popularity features">
**Count distinct users, not events.** One crawler or one obsessive shopper otherwise defines the feature (module 3). This is the same rule as the popularity baseline in module 6, and it is violated just as often here.

**Popularity is the most leak-prone feature you will build.** It is an aggregate over *other users*, so the temptation to compute it once with a global `GROUP BY` is overwhelming — and that single table then contains the test period for every training row. Popularity needs the same as-of treatment as everything else, bucketed by day.

**Raw counts do not transfer across time.** A `pop_long` of 500 means something different in December than in February. `pop_rank_pct` is unitless and stable, which is why it usually outperforms the raw count despite carrying strictly less information.
</ConceptBox>

## Session features

Everything so far is measured in days. A shopper's *current visit* is measured in seconds, and it is the strongest signal you have about what they want **right now**.

<SessionFeatureWidget />

| Feature | Why |
|---|---|
| `last_item` | The single most predictive feature on most e-commerce surfaces |
| `last_n_items` | Intent is a trajectory, not a point |
| `dwell_total`, `s_dwell`, `s_dwell_share` | Attention, not clicks |
| `session_seconds`, `n_events` | Browsing vs. hunting |
| `bounces` | A sub-10s view is a rejection, not interest |
| `repeat_views` | Returning to an item three times is near-purchase intent |
| `top_category`, `cat_share` | The aisle they are standing in |

<ConceptBox title="Dwell time is the point">
Run the widget to the end of Bhavna's session. By **view count** the USB-C Hub beats the Steel Bottle 3 to 1 — a 3× signal. By **dwell** it beats it 439s to 12s, a **37×** signal, taking 81% of the session's total attention.

The Bottle was a 12-second bounce. Counting it as one "view", exactly equal to a 210-second read of the Hub, discards nearly everything the session told you. Views are cheap and near-random; attention is expensive and deliberate.

Two cautions. **Cap dwell** — an abandoned tab reports 4 hours, so clip at something like the 95th percentile (120–300s) or the session will be defined by one person who went to lunch. And **dwell needs a page-exit event** to measure at all, which is a client instrumentation decision, not a modelling one. It belongs in the event contract (module 3).
</ConceptBox>

Two structural properties make session features different from everything else in this module:

- **They work for logged-out and brand-new users.** No profile, no history, no problem — which makes them the standard cold-*user* fix from module 12.
- **They decay in minutes, not days.** Bhavna's session screamed USB-C Hub on day 12; she bought a Keyboard on day 27. Session intent is for *this visit* and the next hour, not for a fortnight out. Serve them on session-scoped surfaces and let long-term features own the homepage.

## Latent features — MF scores as ranker inputs

The ALS model from module 8 produces a score for every (user, item) pair. **That score is a feature.** This is how the two stages actually compose, and it is the fastest way to fix a ranker that has plateaued.

```python
X, Y, _ = als(build_matrix(train), k=64)              # module b4, nightly batch
cand["als_score"] = [float(X[u_ix[u]] @ Y[i_ix[i]])   # one dot product per candidate
                     for u, i in zip(cand.user_id, cand.item_id)]

# the factors themselves are also usable, at a cost
cand["als_user_norm"] = np.linalg.norm(X[cand.user_id.map(u_ix)], axis=1)
for d in range(8):                                     # a few dims, not all 64
    cand[f"als_item_f{d}"] = Y[cand.item_id.map(i_ix)][:, d]
```

Feed the **score**, not the raw factors, as your first move. The score is one well-conditioned column that already encodes the interaction; 128 raw factor columns are noisy, individually meaningless (module 8: the axes are arbitrary), and will bury your handful of genuinely informative features in a tree model.

<ConceptBox title="Why this is composition, not double-counting">
The two models know different things and neither can learn the other's part.

**ALS sees the whole interaction matrix** — every user, every item, all collaborative structure. It cannot see price, stock, device, time of day, or anything about the current session.

**The ranker sees rich context** on a few hundred candidates. It cannot rediscover collaborative structure, because it only has a few thousand labelled rows.

On NovaCart the effect is measurable. Adding decay, the popularity family and `als_score` to the base feature set:

| Model | NDCG@3 | Top feature |
|---|---|---|
| Base features | 0.250 | `ui_days_since` (0.70) |
| + decay / popularity / ALS | **0.377** | `ui_days_since` (0.35), `als_score` (0.24) |
| Recency baseline | 0.438 | — |

The ranker's dependence on `ui_days_since` halves, and `als_score` becomes the second-strongest feature — it stopped being a worse copy of the recency baseline. It still loses to that baseline on 11 positives, which remains a data problem, not a feature problem.

Note also that `ui_decay` scores only 0.017 importance here: it is nearly collinear with `ui_days_since`, and the tree picks one. Redundant features are not free — they split importance and make the model harder to read — so ship the family, then prune it.
</ConceptBox>

<ConceptBox title="Common confusion — a leak hiding inside a good idea">
`als_score` is trained on the interaction matrix. **If ALS was fitted on all data including the test period, every training row's `als_score` contains the future.** This is the module's central bug wearing a different hat, and it is easy to miss because the leak lives one model upstream.

The rule: the ALS model attached to a row dated $t$ must have been trained only on events before $t$. In practice that means refitting per training period (weekly is usually enough) and joining as-of, exactly like any other feature. Teams that get every SQL aggregate right still routinely leak here.
</ConceptBox>

## Encoding high-cardinality IDs

`item_id` has a million values. One-hot is impossible; label encoding invents a false ordering. Three real options:

**Target encoding** — replace the ID with the mean label for that ID. Powerful and leaky by default: the row's own label is in its own encoding. Compute it **out-of-fold and as-of** (only from earlier data), and smooth toward the global mean for rare IDs:

$$\text{enc}(i) = \frac{n_i \bar{y}_i + m \bar{y}}{n_i + m}$$

where $n_i$ is the ID's count so far, $\bar{y}$ the global mean, and $m$ a smoothing constant around 20. An item seen twice gets pulled almost entirely to the global mean; an item seen 10,000 times keeps its own.

**Embeddings** — learn a dense vector per ID inside a neural ranker. Handles cardinality natively, needs a lot of data per ID, and gives a new ID nothing.

**Frequency / count encoding** — replace the ID with how often it appears. Cheap, no leakage, surprisingly effective as a popularity proxy.

## Features you must not build

- **Anything derived from the label.** "Did this session end in a purchase" as a feature for predicting purchase. Obvious in prose, easy to slip in through a joined table.
- **Post-event state.** `item.total_sales` read from today's catalog snapshot, attached to a row from three months ago. The catalog table has no history unless you built it one — which is what a slowly-changing-dimension table is for.
- **Features you cannot compute at serving time.** If `views_30d` takes a 40-second Spark job, it cannot be in a 50 ms request path. Every offline feature needs an online counterpart producing the *same value*, or you get **training/serving skew**: the model learns on one distribution and is served another.
