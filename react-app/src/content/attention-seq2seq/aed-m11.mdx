# Module 11: Limitations of Attention-Based Encoder-Decoder Architecture

<Bridge>
Every module since Module 6 has been about what attention fixed. This one is about what it didn't — the two problems that survive, unrelated to the bottleneck, both traceable to a single design choice this whole track has taken for granted: the encoder and decoder are RNNs.
</Bridge>

## Still one step at a time

<PredictReveal
  prompt="The decoder generates token 5 using its hidden state after generating token 4. Can a GPU compute the RNN update for token 5 before the update for token 4 has finished, even with unlimited parallel hardware?"
  options={["Yes — attention decouples the steps enough to parallelize them", "No — each step's hidden state depends on the previous one, so they must run in order"]}
  correct={1}
>

Attention changed *what* feeds into each decoder step — a fresh $c_i$ instead of a stale $c$ — but it didn't touch *how* the decoder advances: RNN cell, one step, wait for the hidden state, next step. That dependency chain, $s_i$ needs $s_{i-1}$, is exactly as sequential as it was in Module 2. During training, this means $T_{tgt}$ sequential RNN updates per example — no amount of extra GPU hardware collapses that into fewer steps, because each one genuinely needs the previous one's output.

The encoder has the same issue in reverse: it still reads the source sentence one token at a time, so very long source sequences still stress the same **vanishing-influence** pattern Module 5 described for the plain encoder — attention fixed *what the decoder can see*, not *how well the encoder itself represents a very long sequence internally*.

</PredictReveal>

## The cost that attention added, not removed

<PredictReveal
  prompt="Module 8 showed attention costs O(T_src × T_tgt) instead of the plain decoder's O(T_tgt). As both source and target sentences get longer — say, translating full paragraphs — does this cost stay manageable or become a real bottleneck of its own?"
  options={["Stays manageable — the extra cost is negligible at any length", "Becomes a real bottleneck — the cost grows with the product of both lengths"]}
  correct={1}
>

For short sentences, this is a rounding error. For long documents — hundreds or thousands of tokens — $T_{src} \times T_{tgt}$ scoring operations per training example is a genuine cost, and it stacks on top of a decoder that's already forced to run sequentially rather than in parallel. Attention solved the *representational* bottleneck from Module 5 without touching either of these two structural constraints: sequential computation, and score cost that scales with sequence length.

</PredictReveal>

<ConceptBox title="Where this leaves off">
Two questions fall out of this module naturally: could the sequential RNN be dropped entirely, and could attention itself — not just the decoder attending to the encoder, but tokens attending to *each other within the same sequence* — do the representational work RNNs were doing, in parallel instead of one step at a time? That question, and the architecture that answers "yes" to both, is self-attention and the Transformer — the **Transformers** track picks up exactly here.
</ConceptBox>

---

<ConceptBox title="TL;DR">
- Attention fixed the **representational** bottleneck (Module 5) but left the **architectural** one untouched: encoder and decoder are still RNNs.
- Decoder steps remain strictly sequential — $s_i$ depends on $s_{i-1}$ — so no amount of parallel hardware collapses $T_{tgt}$ steps into fewer.
- The encoder still reads token by token, so very long source sequences still face the same vanishing-influence pattern from Module 5, just no longer masked by a single bottleneck vector.
- Attention's own scoring cost, $O(T_{src} \times T_{tgt})$, grows with both sequence lengths — fine for sentences, a real cost for documents.
</ConceptBox>
