**Learning outcome:** explain a Composer deployment and trace a DAG from source file to task execution.

## What is managed, and what you own

Google Cloud Composer manages an Airflow environment. You still own the DAG code, Python dependencies, input contracts, access permissions, external jobs, and failure response. A managed scheduler cannot decide whether a model's features or evaluation are correct.

```text
Versioned DAG source
        |
        v
Environment bucket: dags/ --> Airflow parses DAG --> scheduled run
                                                    |
                                                    v
                                              task workers
                                                    |
                                                    v
                                  data storage / training job / artifacts
```

The environment's Cloud Storage bucket carries DAG files. Task data and model artifacts should use deliberately selected storage locations; the DAG folder is not a model registry.

## Compatibility before deployment

Composer generation and Airflow major version are different version numbers. In particular, do not infer the available Python imports merely from the name **Composer 3**. Inspect your environment's image, Airflow version, Python version, and installed provider packages. Match the DAG from Module 2 to that runtime and test dependencies before upgrading.

An **Airflow provider** is a package containing integrations such as Google Cloud operators and hooks. A hook wraps a service connection; an operator defines an Airflow task. Their APIs follow the installed provider version. Keep a tested dependency specification with the DAG source.

## Optional lab: deploy to an existing environment

This lab requires a Google Cloud project, an existing Composer environment, the Google Cloud CLI, and permission to upload DAGs and view the environment. Composer and jobs can incur charges while provisioned or running. The commands below deploy only the tiny teaching DAG; they do not create a Composer environment or release a real model.

Replace `YOUR_PROJECT`, `YOUR_REGION`, and `YOUR_ENVIRONMENT`. Run these commands from the directory containing the version-compatible `duration_training.py` file:

```bash
gcloud composer environments describe YOUR_ENVIRONMENT \
  --project YOUR_PROJECT --location YOUR_REGION \
  --format="yaml(config.softwareConfig,config.dagGcsPrefix)"

gcloud composer environments storage dags import \
  --project YOUR_PROJECT --environment YOUR_ENVIRONMENT \
  --location YOUR_REGION --source duration_training.py
```

Open the environment's Airflow UI. Allow time for DAG synchronization and parsing, check import errors, and trigger one run. Expected result: the same five tasks and MAE of 1.0 from Module 2. If parsing fails, compare imports and dependencies with the environment runtime before retrying the upload. If execution fails, inspect that task's logs and the external service error.

After the exercise, pause the teaching DAG and remove its file from the environment's DAG storage if no longer needed. Pausing a DAG does not stop the cost of the Composer environment. Remove a dedicated training environment only when its owner confirms no other workflows depend on it.

## Identity and secrets

The identity uploading the DAG and the service account executing tasks can have different permissions. A successful upload therefore does not prove that a task can read a dataset or submit a training job.

Grant task identities only the needed access to specific data, artifacts, and services. Use managed connections or an appropriately configured secrets backend for credentials, rather than embedding keys in source. Verify networking as well as permissions: a worker with access rights still needs a route to the service.
