<ConceptBox title="TL;DR">
- An image is a **2-D (or 3-D) array of integers**. Everything else in this track is arithmetic on that array.
- Shape is `(H, W)` greyscale or `(H, W, 3)` colour. NumPy indexes `img[y, x]` — **row first**, the opposite of the `(x, y)` order drawing functions take.
- **Sampling** decides how many pixels; **quantisation** decides how many values each pixel may hold. Both are lossy, both happen before your model sees anything.
- Greyscale is not the channel average: $0.299R + 0.587G + 0.114B$, because the eye weights green most.
- **HSV** separates colour from brightness; RGB does not. That is why colour thresholding works in HSV and fails in RGB.
</ConceptBox>

## An image is an array

A greyscale image of height $H$ and width $W$ is a function sampled on a grid:

$$I : \{0,\dots,H-1\} \times \{0,\dots,W-1\} \rightarrow \{0,\dots,255\}$$

Two independent discretisations produced it:

| Step | What it discretises | Controlled by | Artefact when too coarse |
|---|---|---|---|
| **Sampling** | position | sensor resolution | aliasing, jagged edges |
| **Quantisation** | intensity | bit depth | banding, posterisation |

A 1920×1080 RGB frame at 8 bits is $1920 \times 1080 \times 3 = 6{,}220{,}800$ bytes — just under 6 MB, uncompressed, for one frame.

## Colour is three arrays stacked

An RGB image is $(H, W, 3)$: three greyscale planes read together. Nothing about that layout says the channels are the *right* three numbers — it is a storage convention, and other conventions are better for other jobs.

<ColorSpaceWidget />

<ConceptBox title="Two conventions that bite">
**BGR, not RGB.** OpenCV's `imread` returns channels in **B, G, R** order for historical reasons. Matplotlib expects RGB. Displaying an OpenCV image directly with `plt.imshow` swaps red and blue — the classic "why is the sky orange" bug. Fix: `img[:, :, ::-1]` or `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)`.

**Row-major indexing.** `img[y, x]` in NumPy, `cv2.rectangle(img, (x, y), ...)` in OpenCV drawing calls. Same library, opposite order.
</ConceptBox>

## Worked example — memory and dtype

A 4000×3000 photo, 3 channels:

$$4000 \times 3000 \times 3 \times 1\text{ byte} = 36{,}000{,}000 \text{ bytes} \approx 34.3 \text{ MiB}$$

Convert it to `float32` for a model and it becomes $4\times$ that — **137 MiB per image**. A batch of 32 is 4.4 GiB before a single layer runs. This is why data pipelines resize *before* converting to float, not after.

```python
import cv2, numpy as np

img = cv2.imread('photo.jpg')          # (3000, 4000, 3), dtype=uint8, BGR
print(img.shape, img.dtype, img.nbytes / 1e6, 'MB')

grey = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)   # (3000, 4000) — channel axis gone
hsv  = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)    # H in [0,179] for uint8, not [0,359]

print(img[100, 200])        # [B G R] at row 100, column 200
print(grey.min(), grey.max(), grey.mean().round(1))
```

Note the OpenCV quirk in that last comment: hue is halved to fit 0–255 in a `uint8`, so "red" is near 0 **or** near 179, not 359.
