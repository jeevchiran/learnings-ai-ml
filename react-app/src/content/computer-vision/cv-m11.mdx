# Module 11: Fully Convolutional Networks for Detection

<ConceptBox title="TL;DR">
- Naive detection = classify every crop of every size at every position. The arithmetic kills it before the accuracy does.
- Neighbouring windows overlap by 80–95%, so a crop-and-classify loop recomputes almost the same features thousands of times.
- A **fully convolutional network** computes them once: replace every `Linear` with an equivalent `Conv2d` and the network accepts any input size and emits a **map** of scores, one per window position, in a single pass.
- The equivalence is exact — an $n \times n \times C \to K$ dense layer *is* a $n \times n$ convolution with $K$ filters.
- What you get is a score map at **output stride** $s$ = the product of all strides. That map is the substrate every later detector predicts on.
</ConceptBox>

<Bridge>
Module 10 assumed a detector that emits candidate boxes. This module is where those candidates start coming from — and why the obvious approach, sliding a classifier, had to be abandoned for something that shares computation.
</Bridge>

## The naive cost

Slide a $w \times w$ window with stride $s$ over a $W \times H$ image, at $L$ pyramid scales:

$$N = \sum_{\ell=1}^{L} \left\lfloor\frac{W_\ell - w}{s} + 1\right\rfloor \left\lfloor\frac{H_\ell - w}{s} + 1\right\rfloor$$

Two objections, and only one has a fix:

- **Too many windows.** Fixable — that is the rest of this module.
- **A window is a bad prior.** Even with a pyramid, you are betting that some rectangle in your fixed set fits the object. Not fixable here; Module 12's region proposals and Module 18's anchors are the two answers.

## Convolutionalising a classifier

A `Linear(n·n·C, K)` applied to a flattened $n\times n\times C$ feature map is a dot product of $K$ weight vectors with that map. So is a `Conv2d(C, K, kernel_size=n)` applied to the same map — same weights, reshaped.

```python
import torch, torch.nn as nn

fc   = nn.Linear(7 * 7 * 512, 4096)
conv = nn.Conv2d(512, 4096, kernel_size=7)
conv.weight.data = fc.weight.data.view(4096, 512, 7, 7)   # exactly the same numbers
conv.bias.data   = fc.bias.data
```

Nothing about the computation changed for a $7\times7$ input — both emit $4096$ numbers. The difference appears on a **larger** input: the `Linear` version cannot run at all (shape mismatch), while the `Conv2d` version slides and emits a $4096$-channel *map*, one column per window position. That single observation is OverFeat (Sermanet et al., 2013), and it is the foundation under every dense detector since.

<ConceptBox title="What the score map actually is">
For a VGG-style backbone with five stride-2 pooling stages, the **output stride** is $2^5 = 32$. Feed a $512\times512$ image and you get a $16\times16$ score map: 256 window evaluations, computed in one pass, each corresponding to a $224\times224$ receptive field stepping 32 pixels at a time.

Fine detail is the price. Objects smaller than the stride can fall between positions entirely — the small-object problem that Modules 18 and 19 attack with multi-scale feature maps.
</ConceptBox>

## Worked example — the saving, exactly

$512\times512$ image, $64\times64$ window, stride 8, single scale:

$$N = \left(\frac{512-64}{8}+1\right)^2 = 57^2 = 3{,}249 \text{ windows}$$

Let one window forward pass cost $c$. Naive: $3{,}249\,c$.

Convolution cost scales with input area, so one pass over the full image costs

$$c \cdot \frac{512^2}{64^2} = 64\,c$$

$$\text{speed-up} = \frac{3249}{64} \approx \mathbf{50.8\times}$$

Halve the stride to 4 and $N$ quadruples to $12{,}769$ while the FCN cost does not move at all — the speed-up becomes 200×. **The saving is exactly the redundancy**, and the redundancy grows as you look more finely.

## Where this leads

| Approach | How candidates arise | Modules |
|---|---|---|
| Sliding window + FCN | every position of a dense map | this module |
| Region proposals | a separate algorithm nominates ~2000 regions | 12–13 |
| Anchors on a dense map | $k$ box shapes per map position | 13, 18–19 |
| Dense grid regression | each cell directly regresses boxes | 15–17 |

Note that three of the four are **still fully convolutional**. FCN did not lose to region proposals; it became the backbone that region proposals run on top of.

<DerivationSteps>
<DerivationStep number={1} title="Output size and output stride">

For one layer with kernel $k$, padding $p$, stride $s$:

$$H_{\text{out}} = \left\lfloor \frac{H_{\text{in}} + 2p - k}{s}\right\rfloor + 1$$

Stack $L$ layers and the **output stride** — how many input pixels one output step covers — is the product:

$$s_{\text{total}} = \prod_{\ell=1}^{L} s_\ell$$

Padded $3\times3$ convolutions with stride 1 contribute a factor of 1, so only the pooling and strided layers matter. Five stride-2 stages give 32, which is why detection feature maps are so often $\tfrac{1}{32}$ of the input.

The **receptive field** grows differently — additively through the strides:

$$r_{\ell} = r_{\ell-1} + (k_\ell - 1)\prod_{i<\ell} s_i$$

so a deep layer can have a receptive field far larger than the stride. That is what lets a $16\times16$ map say something meaningful about $224\times224$ regions.

</DerivationStep>

<DerivationStep number={2} title="Why the FC → conv equivalence is exact">

Let the feature map be $\mathbf{X} \in \mathbb{R}^{n \times n \times C}$ and the dense layer $\mathbf{W} \in \mathbb{R}^{K \times n^2C}$. Flattening gives

$$y_k = \sum_{i=1}^{n}\sum_{j=1}^{n}\sum_{c=1}^{C} W_{k,\,(i,j,c)}\, X_{i,j,c} + b_k$$

A convolution with kernel size $n$, $C$ input channels and $K$ filters, evaluated at its single valid position, computes

$$z_k = \sum_{i=1}^{n}\sum_{j=1}^{n}\sum_{c=1}^{C} K_{k,c,i,j}\, X_{i,j,c} + b_k$$

Identical, under the index identification $K_{k,c,i,j} = W_{k,(i,j,c)}$ — which is precisely the `.view(K, C, n, n)` in the code above. The two layers are the same function; only their *domain* differs. The dense one is defined on exactly one input size; the conv one is defined on all of them.

</DerivationStep>
</DerivationSteps>
