## The Problem: Many Settings, Expensive Scoring

Cross-validation scores *one* hyperparameter setting honestly — but that's $K$ model fits, not a cheap lookup. With several hyperparameters each having several values, the number of settings explodes combinatorially. This module is about spending a limited evaluation budget well.

## Grid Search: Exhaustive but Expensive

**Grid search** tries every combination in the Cartesian product of specified values.

```python
from sklearn.model_selection import GridSearchCV
from sklearn.ensemble import RandomForestClassifier

param_grid = {
    'n_estimators': [100, 200, 300, 400, 500],
    'max_depth': [4, 6, 8, 10, 12],
    'min_samples_leaf': [1, 2, 5, 10, 20],
}
grid = GridSearchCV(RandomForestClassifier(random_state=42), param_grid, cv=5, scoring='f1', n_jobs=-1)
grid.fit(X_train, y_train)
print(grid.best_params_, grid.best_score_)
```

Cost grows **multiplicatively**: 5×5×5 = 125 settings × 5-fold CV = 625 fits. A fourth hyperparameter (5 values) jumps to 3,125 settings (15,625 fits). Grid search scales as (values)^(hyperparameters) — its own curse of dimensionality.

## Random Search: Sample Instead of Enumerate

**Random search** samples a fixed number of settings from distributions.

```python
from sklearn.model_selection import RandomizedSearchCV
from scipy.stats import randint

param_dist = {'n_estimators': randint(100, 500), 'max_depth': randint(3, 15), 'min_samples_leaf': randint(1, 20)}

random_search = RandomizedSearchCV(
    RandomForestClassifier(random_state=42), param_dist,
    n_iter=60,          # budget, decoupled from #hyperparameters
    cv=5, scoring='f1', random_state=42, n_jobs=-1)
random_search.fit(X_train, y_train)
```

### Why Random Often Beats Grid

The **Bergstra & Bengio** result: in most models only a few hyperparameters matter much; the rest are near-flat. Grid search spends its budget *evenly across every axis* — if `min_samples_leaf` barely matters, it still tries all 5 values combined with everything else, re-testing near-equivalent points. Random search never repeats a value along any axis, so its samples project to a denser, more varied set along *each* hyperparameter — including the ones that matter. More effective exploration of the important dimensions, for free.

## Bayesian Optimization: Learn From Past Trials

Grid and random treat every evaluation independently. **Bayesian optimization** uses what it learned:

1. Fit a probabilistic **surrogate** (often a Gaussian Process) over the space from the (setting, score) pairs so far — it predicts expected score *and* uncertainty for any untried setting.
2. An **acquisition function** picks the next setting, balancing **exploitation** (near the current best) against **exploration** (high-uncertainty regions).
3. Evaluate with real CV, update the surrogate, repeat.

Because each choice is informed by all previous ones, it reaches a good setting in far fewer evaluations — valuable when each CV run is expensive (a large neural net can take hours).

```python
from skopt import BayesSearchCV
from skopt.space import Integer

bayes_search = BayesSearchCV(
    RandomForestClassifier(random_state=42),
    {'n_estimators': Integer(100, 500), 'max_depth': Integer(3, 15), 'min_samples_leaf': Integer(1, 20)},
    n_iter=40, cv=5, scoring='f1', random_state=42)
bayes_search.fit(X_train, y_train)
```

`optuna` is another common choice; the tool matters less than the idea — **use past results to guide future trials.**

## Successive Halving / Hyperband

The above treat each evaluation as all-or-nothing. But training cost often scales with a controllable **resource** — boosting rounds, epochs, or data fraction. **Successive halving** exploits this:

1. Start with many configs, each on a small budget.
2. Score, keep the top fraction (e.g. best third).
3. Give survivors a bigger budget, repeat.
4. Continue until a few remain, evaluated at full budget.

Bad configs die early and cheaply, so most compute goes to promising ones. **Hyperband** runs several halving brackets with different starting budgets, hedging the elimination schedule.

```python
from sklearn.experimental import enable_halving_search_cv  # noqa
from sklearn.model_selection import HalvingRandomSearchCV

halving_search = HalvingRandomSearchCV(
    RandomForestClassifier(random_state=42), param_dist,
    resource='n_samples',   # grow training subset each round
    factor=3,                # keep ~1/3 of candidates each round
    cv=5, scoring='f1', random_state=42)
halving_search.fit(X_train, y_train)
```

<ConceptBox title="More evaluations isn't automatically better">
"60 trials good, 600 better" holds only up to your budget — marginal improvement per trial shrinks fast near the best achievable score. You're really optimizing **score per unit of compute**. That's why random search, Bayesian optimization, and Hyperband exist instead of ever-bigger grids: reach a comparable score with a smaller budget by spending evaluations smartly, not by spending more.
</ConceptBox>

## Practice

#### Problem 1: Estimating Search Cost
4 hyperparameters, 6 values each, 5-fold CV. Grid-search fits? Random search with `n_iter=100`?

**Solution:** Grid: $6^4 = 1{,}296$ settings × 5 = **6,480 fits**. Random: $100 \times 5 =$ **500 fits** — ~13× cheaper, and (per Bergstra & Bengio) often comparably good if only 1–2 hyperparameters matter.

#### Problem 2: Choosing a Strategy
Gradient-boosted trees, each train+CV-fold ≈ 20 min, tight deadline. Which strategy, and why not grid?

**Solution:** With expensive evaluations and a hard budget, get the most from few trials — Bayesian optimization (or Hyperband/successive halving, since boosted trees' cost scales with the number of trees) fits well: each trial informs the next or kills weak configs early. Plain grid's cost is fixed by grid size regardless of early results; you can't adapt it to the deadline without gutting coverage or running out of time mid-search.
