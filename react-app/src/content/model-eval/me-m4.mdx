## The problem: many settings, expensive scoring

Cross-validation (Module 3) gives you an honest score for *one* hyperparameter setting — train a random forest with `max_depth=8, n_estimators=200`, run 5-fold CV, get a trustworthy number back. But models have many hyperparameters, and you rarely know the best values up front. This module is about searching that space efficiently instead of guessing.

Every hyperparameter setting requires a full CV run to score honestly — that's not a cheap lookup, it's $K$ model fits. If you have several hyperparameters, each with several candidate values, the number of settings to try can explode combinatorially. The rest of this module is about strategies for spending a limited evaluation budget well.

## Grid Search: exhaustive but expensive

**Grid search** specifies a fixed set of candidate values for each hyperparameter and tries every combination in the Cartesian product.

```python
from sklearn.model_selection import GridSearchCV
from sklearn.ensemble import RandomForestClassifier

param_grid = {
    'n_estimators': [100, 200, 300, 400, 500],
    'max_depth': [4, 6, 8, 10, 12],
    'min_samples_leaf': [1, 2, 5, 10, 20],
}

grid = GridSearchCV(
    RandomForestClassifier(random_state=42),
    param_grid=param_grid,
    cv=5,
    scoring='f1',
    n_jobs=-1,
)
grid.fit(X_train, y_train)
print(grid.best_params_, grid.best_score_)
```

The cost grows **multiplicatively** with each hyperparameter you add. Here, 5 values × 5 values × 5 values = 125 distinct settings, and each setting needs a full 5-fold CV to score — so the real cost is $125 \times 5 = 625$ model fits, just for this one grid. Add a fourth hyperparameter with 5 values and it jumps to 3,125 settings (15,625 fits). This is grid search's curse of dimensionality: it scales as (values per hyperparameter)^(number of hyperparameters).

## Random Search: sampling instead of enumerating

**Random search** samples a fixed number of hyperparameter settings from specified distributions, rather than trying every combination on a fixed grid.

```python
from sklearn.model_selection import RandomizedSearchCV
from scipy.stats import randint, uniform

param_dist = {
    'n_estimators': randint(100, 500),
    'max_depth': randint(3, 15),
    'min_samples_leaf': randint(1, 20),
}

random_search = RandomizedSearchCV(
    RandomForestClassifier(random_state=42),
    param_distributions=param_dist,
    n_iter=60,          # fixed budget, independent of grid size
    cv=5,
    scoring='f1',
    random_state=42,
    n_jobs=-1,
)
random_search.fit(X_train, y_train)
```

You control the budget directly with `n_iter`, decoupled from how many hyperparameters you're tuning.

### Why random search often beats grid search

This is the classic **Bergstra & Bengio** result, and the intuition is worth internalizing rather than just citing. In most real models, only a handful of hyperparameters actually matter much for performance — the rest have a small or flat effect across their reasonable range.

Grid search spends its budget **evenly across every axis**, whether or not that axis matters. If `min_samples_leaf` barely affects your score, grid search still tries all 5 of its values, combined with all combinations of the other hyperparameters — most of that effort is redundant, because along the unimportant axis you're re-testing points that are all roughly equivalent.

Random search never repeats a value along any single axis (with continuous distributions, essentially every sampled value is unique). So even with the same budget, random search's samples project down to a denser, more varied set of values along *each individual* hyperparameter — including whichever ones actually matter. You get more effective exploration of the important dimensions, for free, simply because you didn't waste structure enforcing a grid on the unimportant ones.

## Bayesian Optimization: learning from past evaluations

Grid and random search treat each evaluation independently — neither one uses what it learned from earlier trials to decide where to look next. **Bayesian optimization** does.

The core idea:

1. Fit a probabilistic **surrogate model** (commonly a Gaussian Process, but the idea generalizes) over the hyperparameter space, using the (setting, CV score) pairs evaluated so far. This surrogate predicts, for any untried setting, an expected score *and* an uncertainty estimate.
2. Use an **acquisition function** to pick the next setting to actually evaluate — balancing **exploitation** (try settings near the best score found so far) against **exploration** (try settings the surrogate is still very uncertain about, since they might hide something better).
3. Evaluate that setting with real CV, update the surrogate with the new data point, and repeat.

Because each choice of what to try next is informed by everything learned so far, Bayesian optimization typically reaches a good setting in far fewer evaluations than grid or random search — valuable when each evaluation is expensive (e.g. CV-ing a large neural network can take hours).

```python
# using scikit-optimize's drop-in replacement for GridSearchCV
from skopt import BayesSearchCV
from skopt.space import Integer

bayes_search = BayesSearchCV(
    RandomForestClassifier(random_state=42),
    search_spaces={
        'n_estimators': Integer(100, 500),
        'max_depth': Integer(3, 15),
        'min_samples_leaf': Integer(1, 20),
    },
    n_iter=40,
    cv=5,
    scoring='f1',
    random_state=42,
)
bayes_search.fit(X_train, y_train)
```

`optuna` is another widely used library for this (and also implements several of the pruning strategies below); the specific tool matters less than the idea: **use past results to guide future trials instead of choosing them blind.**

## Successive Halving / Hyperband

Everything above treats each evaluation as all-or-nothing: train fully, then score with CV. But for many models, training cost scales with a controllable **resource** — number of boosting rounds, epochs, or fraction of the training data used. **Successive halving** exploits this:

1. Start with many candidate configurations, each given a small budget (e.g. a few epochs, or a small data subsample).
2. Score them all, keep only the top fraction (e.g. the best half or third).
3. Give the survivors a bigger budget and repeat.
4. Continue until one (or a few) configurations remain, now evaluated with the full budget.

Bad configurations are eliminated early and cheaply, so most of the compute budget ends up spent on the configurations that are actually promising — rather than giving every candidate a full, expensive training run up front. **Hyperband** extends this idea by running several successive-halving brackets with different starting budgets, hedging against picking too aggressive or too conservative an elimination schedule.

```python
from sklearn.experimental import enable_halving_search_cv  # noqa
from sklearn.model_selection import HalvingRandomSearchCV

halving_search = HalvingRandomSearchCV(
    RandomForestClassifier(random_state=42),
    param_distributions=param_dist,
    resource='n_samples',   # grow the training subset each round
    factor=3,                # keep ~1/3 of candidates each round
    cv=5,
    scoring='f1',
    random_state=42,
)
halving_search.fit(X_train, y_train)
```

`HalvingGridSearchCV` is the exhaustive-grid counterpart when you want successive halving over a fixed grid rather than random sampling.

<ConceptBox title="More evaluations isn't automatically better">
It's tempting to think "if 60 random search trials are good, 600 must be strictly better." That's true only up to your compute budget — more evaluations costs more compute, and past a point the marginal improvement per extra trial shrinks fast (diminishing returns as you approach the best achievable score for that model class).

In practice you're not optimizing score in isolation — you're optimizing **score per unit of compute spent searching**. That reframing is exactly why random search, Bayesian optimization, and Hyperband exist instead of everyone just running ever-bigger grids: they aim to reach a comparable or better score using a smaller budget, by spending evaluations more intelligently (denser coverage of important axes, learning from past trials, or eliminating bad configurations early) rather than simply spending more.
</ConceptBox>

## Practice

#### Problem 1: Estimating search cost

You're tuning 4 hyperparameters, 6 candidate values each, with 5-fold CV. How many total model fits does an exhaustive grid search require? If you instead ran random search with `n_iter=100`, how many total model fits would that require?

**Solution:** Grid search: $6^4 = 1{,}296$ distinct settings, each scored with 5-fold CV, so $1{,}296 \times 5 = 6{,}480$ total model fits. Random search with `n_iter=100`: $100 \times 5 = 500$ total model fits — roughly 13x cheaper, while (per Bergstra & Bengio) still often finding a comparably good setting if only 1-2 of the 4 hyperparameters actually matter much.

#### Problem 2: Choosing a strategy

You're tuning a gradient boosted tree model where each individual training run (for one hyperparameter setting, one CV fold) takes about 20 minutes, and you have a small, fixed number of hours before a deadline. Which search strategy fits best, and why would you avoid plain grid search here?

**Solution:** With expensive individual evaluations and a hard time budget, you want a strategy that gets the most out of a small number of trials — Bayesian optimization (or Hyperband/successive halving, since boosted trees' training cost scales naturally with number of trees/rounds) fits well, because each evaluates informs where to look next or eliminates weak configurations early, rather than treating every trial as an independent shot in the dark. Plain grid search would be a poor fit: its cost is fixed by the grid size regardless of how informative early results are, so you can't adapt it to a tight deadline — you'd either have to shrink the grid so much that you lose meaningful coverage, or risk running out of time mid-search.
