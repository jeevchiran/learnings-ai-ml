## More Columns Isn't Free

Modules 1–4 took the feature set as fixed. This module asks the question that comes *before*: which features should be in the dataset at all?

The instinct — more features can only help, the model ignores the useless ones — is wrong often enough to be dangerous. Extra columns cost you in ways that surface only after training: the data gets sparser, noise features add variance, redundant features destabilize some models, and every column taxes training time, inference time, and interpretability. This module builds the vocabulary — the curse of dimensionality, selection vs. reduction, and the filter/wrapper/embedded taxonomy.

## The Curse of Dimensionality

Fix your sample count and add features. Two problems appear, both from geometry, not from any specific dataset.

**Covering space gets exponentially harder.** To cover a space at spacing 0.1 per axis: 10 points in 1D, but $10^{10}$ in 10D. Points needed for fixed density grow as $k^d$ — exponential in $d$. Your sample count is fixed, so past a handful of features it covers a vanishing fraction of the space. Data doesn't get "a little sparser" — it gets catastrophically sparser.

**Distances stop discriminating.** k-NN, clustering, and kernel methods assume "nearby" points are more alike. In high dimensions, for $n$ points as $d \to \infty$:

$$\frac{\text{dist}_{\max} - \text{dist}_{\min}}{\text{dist}_{\min}} \to 0$$

The gap between closest and farthest neighbour, relative to the closest, shrinks toward zero — every point looks equidistant from every other. A Euclidean distance sums many per-coordinate contributions, and that sum concentrates around its mean as terms grow, so the *relative* spread vanishes. Once every pairwise distance is within a few percent of every other, "nearest neighbour" stops meaning anything.

## Why More Features Isn't Always Better

Three concrete costs, even setting geometry aside:

- **Noise features add variance without signal.** An irrelevant feature is one more degree of freedom to fit chance patterns in *this* training draw — higher variance, larger train/test gap, the overfitting signature from Module 1.
- **Redundant features destabilize some models.** Two highly correlated features make a linear/logistic model unable to cleanly attribute the outcome — coefficients flip and inflate (multicollinearity). Trees are more robust, but redundancy still costs the next item.
- **More features → slower, less interpretable.** Train/inference time scales with feature count; a 20-feature coefficient table is readable, a 2,000-feature one isn't. When you must explain *why* (to a regulator, clinician, stakeholder), a curated feature set often beats a marginal accuracy gain.

## Selection vs. Reduction

Two distinct ways to shrink dimensionality, easily conflated:

- **Dimensionality reduction** builds *new* features combining the originals (PCA projects onto max-variance directions). A principal component is a weighted mix of every column — no longer "age" or "income".
- **Feature selection** keeps a *subset* of the original features, each still interpretable in its original units.

This track is entirely about **feature selection** — which original columns to keep. PCA and projection are out of scope.

## The Three-Way Taxonomy

| Approach | How it scores | Model-aware? | Cost | Risk |
|---|---|---|---|---|
| **Filter** | Statistic between each feature and target (correlation, chi², MI), no model | No | Very low | Ignores interactions — a jointly useful pair scores low alone |
| **Wrapper** | Real model's CV performance on candidate subsets | Yes | High (many fits) | Can overfit selection to the model/CV split |
| **Embedded** | Selection as a byproduct of training (L1 zeros, tree importance) | Yes, one family | Medium | Tied to that model's assumptions |

Filter methods are cheapest and the natural first pass (Module 6). Wrapper and embedded trade speed for interaction-awareness (Module 7).

<ConceptBox title="'Feature selection always improves accuracy' — false">
Its honest goals are **generalization** (less noise variance), **speed**, and **interpretability** — not a guaranteed accuracy bump. A well-regularized model given *all* features (L1 or a tuned tree) can beat aggressive hand-pruning, because regularization down-weights noise without risking the loss of a quietly-useful feature. Removing a feature helps only when it removes *noise*; remove real non-redundant signal and you've just thrown away information.
</ConceptBox>

## Practice

#### Problem 1: Diagnosing the Curse
500 rows, 300 features, k-NN on all of them, no preprocessing. Why is this likely poor regardless of $k$?

**Solution:** 500 points can't densely cover 300 dimensions — most of the space near any test point is empty. And in 300D the nearest/farthest distance ratio is near 1 for most points, so the neighbours k-NN picks aren't meaningfully more similar than the ones it doesn't. Both break k-NN's core assumption before any $k$ can fix it. Reduce features first.

#### Problem 2: Filter vs. Wrapper vs. Embedded
10,000 features, 2,000 rows, budget for only a few model fits. Which category, and why not the alternative?

**Solution:** Filter — each feature scored by a closed-form statistic, so scoring 10,000 costs about the same as scoring one, no fitting. Wrapper methods train and CV a model per candidate subset; with 10,000 features that's an enormous number of full CV loops, exactly what the budget rules out. Filter down to a few hundred, then optionally a lighter wrapper/embedded pass on the survivors.
