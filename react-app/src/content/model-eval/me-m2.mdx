## Splitting the Data Three Ways

Training error can't judge a model, so evaluate on data it never touched while fitting. Split the dataset into up to three disjoint pieces, each with a distinct job:

| Split | Used for | Touched |
|---|---|---|
| **Training** | Fitting parameters (weights, splits, coefficients) | Every training run |
| **Validation** | Comparing models, tuning hyperparameters (degree, `alpha`, `max_depth`, $k$) | Once per candidate |
| **Test** | One final, honest estimate of generalization | **Exactly once**, at the end |

<SplitWidget />

The test-set rule is easy to state and easy to violate: **use it exactly once, after every modeling decision is locked in.** Never to pick a model, tune a knob, decide when to stop, or choose features. The moment a decision is made from the test score, it stops being an honest estimate — you've begun fitting to it, one comparison at a time.

## The Holdout Method

Simplest validation: randomly split off 20–30% as validation, train on the rest.

```python
from sklearn.model_selection import train_test_split
from sklearn.tree import DecisionTreeClassifier
from sklearn.datasets import load_breast_cancer

X, y = load_breast_cancer(return_X_y=True)
X_train, X_val, y_train, y_val = train_test_split(X, y, test_size=0.25, random_state=0)

model = DecisionTreeClassifier(max_depth=4, random_state=0).fit(X_train, y_train)
print(model.score(X_val, y_val))   # validation accuracy
```

Fast and often enough for large data — but the validation score is itself a **noisy estimate**, depending on which rows landed in validation. Change only the split seed and the same model reports different accuracy:

```python
for seed in [0, 1, 2, 3, 4]:
    X_train, X_val, y_train, y_val = train_test_split(X, y, test_size=0.25, random_state=seed)
    model = DecisionTreeClassifier(max_depth=4, random_state=0).fit(X_train, y_train)
    print(f"seed={seed}: val accuracy = {model.score(X_val, y_val):.3f}")

# seed=0: 0.930   seed=1: 0.902   seed=2: 0.951   seed=3: 0.916   seed=4: 0.937
```

Same model, same data — a 5-point swing (0.902–0.951) purely from the split. If two candidates truly differ by 1–2 points, one unlucky split can crown the worse one. One split gives one sample of validation performance, and one sample has variance.

## Stratification

A plain random split can distort class balance. On 95% negative / 5% positive data, a random 25% validation set might come out 3% or 7% positive by chance — enough to move precision/recall with no model change. **Stratified splitting** preserves each class's proportion in train and validation:

```python
X_train, X_val, y_train, y_val = train_test_split(X, y, test_size=0.25, random_state=0, stratify=y)
```

`stratify=y` costs nothing and removes one source of split noise — default for classification, near-mandatory when a class is a small minority.

## When One Holdout Isn't Enough

1. **Small datasets** — carving 25% for validation strips scarce training signal, and the validation estimate on a small slice is especially high-variance.
2. **Split-sensitive decisions** — comparisons on a single split can flip with the split's luck; you can't tell a real 1-point gain from noise.

Same root cause: one split = one sample of "how does this do on unseen data," not enough to separate real differences from split noise. The fix: evaluate across *several* train/validation partitions and combine — cross-validation, next module.

<ConceptBox title="Tuning on the test set is training on it">
A common mistake: try several hyperparameters, score each *on the test set*, keep the best. No gradient touched it — but using its score to make a choice optimizes against those specific examples. Try enough settings and one scores well by chance, exactly like trying enough seeds turns up a lucky split. The reported "test accuracy" is now contaminated — Module 1's overfitting, applied to hyperparameter choices. The fix is procedural: every comparison goes through validation (or CV); the test set is touched once, after everything is decided.
</ConceptBox>

## Practice

#### Problem 1: A Suspicious Split
Model A scores 87.2%, Model B 87.9% on one split. Changing only `random_state`, A now scores 88.4%, B 86.6% — the ranking flips. What does this mean, and what next?

**Solution:** The ~1-point differences are within the noise from which rows land in validation — a single split can't resolve these two models. Picking a winner from either split trusts noise as signal. Evaluate both across multiple splits (cross-validation) and compare averages, which averages out split-to-split variance.

#### Problem 2: Stratify or Not?
Splitting a fraud dataset with 2% positives, `test_size=0.2`. Use `stratify=y`? What goes wrong without it?

**Solution:** Yes. With 2% positives, a random split can yield 0.5% or 4% fraud by chance, distorting precision/recall for reasons unrelated to model quality. `stratify=y` forces both splits to preserve the ~2% rate, removing that noise at no cost.
