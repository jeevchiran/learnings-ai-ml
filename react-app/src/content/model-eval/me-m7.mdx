## Wrapper Methods: Let a Model Vote on Subsets

Filter methods (Module 6) score each feature *on its own*, so they miss interactions — two mediocre features that become powerful only together (like `latitude` and `longitude`, useless alone, jointly a location). Wrapper and embedded methods close the gap by involving a real model, which sees interactions because it's fit on feature *combinations*.

A **wrapper** treats selection as search: try subsets, fit the real model on each, use its cross-validated performance to choose. More expensive than a filter (many model fits), but it optimizes the thing you care about — how *this* model does with *these* features — not a proxy statistic.

### Recursive Feature Elimination (RFE)

Works backward from the full set:

1. Fit on all remaining features.
2. Rank by the model's importance (coefficient magnitude, or `feature_importances_`).
3. Drop the weakest.
4. Refit and repeat to the target count.

```python
from sklearn.feature_selection import RFE
from sklearn.linear_model import LogisticRegression

rfe = RFE(estimator=LogisticRegression(max_iter=1000), n_features_to_select=10)
rfe.fit(X_train, y_train)
print(rfe.support_)          # boolean mask of selected features
print(rfe.ranking_)          # 1 = selected, higher = eliminated earlier
```

Plain `RFE` needs `n_features_to_select` up front — guessing defeats the purpose. `RFECV` wraps elimination in cross-validation and picks the best subset size for you:

```python
from sklearn.feature_selection import RFECV
from sklearn.model_selection import StratifiedKFold

rfecv = RFECV(estimator=LogisticRegression(max_iter=1000), step=1, cv=StratifiedKFold(5), scoring='accuracy')
rfecv.fit(X_train, y_train)
print(rfecv.n_features_)     # CV-chosen count, no guesswork
```

**Cost:** plain RFE with `step=1` is ~$O(\text{n\_features})$ fits; `RFECV` multiplies by folds. For a slow model on a wide dataset, this adds up — RFE trades compute for seeing interactions a filter can't.

### Sequential Feature Selection

A simpler greedy search, two directions:

- **Forward** — start empty, add the feature that most improves CV score each round.
- **Backward** — start with all, remove the feature that costs CV score the least.

```python
from sklearn.feature_selection import SequentialFeatureSelector
from sklearn.linear_model import LogisticRegression

model = LogisticRegression(max_iter=1000)
sfs_forward  = SequentialFeatureSelector(model, n_features_to_select=10, direction='forward', cv=5).fit(X_train, y_train)
sfs_backward = SequentialFeatureSelector(model, n_features_to_select=10, direction='backward', cv=5).fit(X_train, y_train)
```

Both are **greedy** — commit to the locally-best move and never reconsider, so neither guarantees the global best. They can even land on *different* subsets from the same data, for structural reasons:

- **Forward** evaluates each feature in the context of what's already added. A feature useless alone but powerful paired with one not yet in the set looks unremarkable early and may never get added.
- **Backward** starts with everything present, so its first eliminations happen amid all interactions. A feature that seems redundant *because* another is still present might get dropped before backward ever tests life without that other one.

Neither bias is wrong — running both and comparing is often more informative than trusting either.

## Embedded Methods: Selection Built Into Training

No separate search loop — selection is a side effect of how the model fits.

### L1 (Lasso): Coefficients to Exactly Zero

Ridge (L2) penalizes squared coefficients, $\lambda \sum_i \beta_i^2$ — shrinks smoothly toward zero but essentially never *to* zero, keeping all features. Lasso (L1) penalizes absolute size:

$$\lambda \sum_i |\beta_i|$$

That difference has a geometric consequence: L1's constraint region is a diamond with corners *on* the axes (where coefficients are exactly zero); the loss contours first touch it disproportionately at those corners. L2's smooth circle has no corners to land on, so it shrinks without eliminating.

```python
from sklearn.linear_model import Lasso, LogisticRegression
import numpy as np

lasso = Lasso(alpha=0.05).fit(X_train, y_train)
print(f"{np.sum(lasso.coef_ == 0)} of {X_train.shape[1]} features zeroed out by L1")

log_reg_l1 = LogisticRegression(penalty='l1', solver='liblinear', C=1.0).fit(X_train, y_train)
selected = np.where(log_reg_l1.coef_[0] != 0)[0]
```

Larger `alpha` zeroes more coefficients; tune it with CV like any hyperparameter.

### Tree-Based Importance

Tree ensembles give `feature_importances_` for free: roughly the total impurity reduction (Gini/entropy) from splits on that feature, summed across trees and normalized to sum to 1.

```python
from sklearn.ensemble import RandomForestClassifier
import pandas as pd

rf = RandomForestClassifier(n_estimators=300, random_state=42).fit(X_train, y_train)
importances = pd.Series(rf.feature_importances_, index=X_train.columns)
importances.sort_values(ascending=False).head(10)
```

**Caveat:** impurity importance is biased toward high-cardinality/continuous features — more possible split thresholds means more chances to look useful. **Permutation importance** (`sklearn.inspection.permutation_importance`) is more reliable: it measures how much CV score drops when a feature's values are shuffled — actual predictive contribution, not a training-time proxy.

## Comparing the Three Families

| Method | Model-aware? | Interactions? | Cost | Use case |
|---|---|---|---|---|
| Filter (M6) | No | No | Very low (one pass) | Fast first pass on wide data; pre-filter before a wrapper |
| Wrapper (RFE, sequential) | Yes | Yes | High (many refits) | Moderate feature counts where model performance is the criterion |
| Embedded (Lasso, trees) | Yes | Partially | Low-moderate (one fit) | Default for linear (L1) or tree ensembles already in the pipeline |

<ConceptBox title="Are embedded methods strictly better than filters?">
No — they're **model-specific**, a real limitation. Lasso's zeroed coefficients reflect what a *linear* model finds irrelevant; a feature with a nonlinear or threshold relationship can be zeroed by L1 yet be the best split at a tree's root. Tree importance has the mirror problem. The right method depends on the final model you deploy — selecting with Lasso then deploying a random forest throws away exactly the information you wanted. The selection step should be aware of, ideally identical to, the model doing the final prediction.

## Practice

#### Problem 1: RFE or Lasso?
Logistic regression, 40 features, 5,000 rows, fast to fit. `RFECV` or `LogisticRegression(penalty='l1')` first?

**Solution:** Both are affordable. `RFECV` is a good default when refitting is cheap — it directly optimizes CV score over feature count with no `alpha` to tune (just ≤40 refits per fold). L1 is one fit but needs its `C` tuned to land on a sensible number of survivors, usually a small CV search over `C`. Prefer L1 if you already need to tune regularization for overfitting — selection rides along for free.

#### Problem 2: Forward/Backward Disagreement
Forward picks `{A,B,C}`, backward picks `{A,D,E}`, same model/CV, both targeting 3. Is one wrong?

**Solution:** Not necessarily. Both are greedy, exploring only a slice of all 3-feature subsets, each biased differently — forward may never test `D,E` together (neither looked good enough alone to add early); backward saw `D,E` amid all features and only dropped the ones most redundant given everything else. Without exhaustively scoring every subset you can't call either wrong — the disagreement is useful; evaluate both with a final CV comparison.
